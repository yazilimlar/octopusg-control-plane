## What was built, and what was not

The owner directed a read-only DayOS monitor. The written slice specification
([NEXT-SLICE-DAYOS-MONITORING](../NEXT-SLICE-DAYOS-MONITORING.md)) covers Supabase metadata only and is
blocked on credentials, which the same directive forbids, so **it was not implemented and OG-CONN-015 is
unchanged**. What was built is the surface the directive's scope describes: the DayOS source repository,
checkout, branch, HEAD, working tree, deployment reference and drift, through the existing observer,
truth model, catalog, drift model, connection records and open-action policy. No parallel monitoring
architecture exists; the new module (`src/monitor.ts`) only composes those.

**Authoritative source, from evidence.** The registry (v1.6, pinned) records DayOS as
`projects[dayos].git_state` on branch `feature/dayos-next-integration-preview`, and records the checkout
of that same branch on `projects[artemis-omni].current_local_paths[0]` (role "DayOS feature checkout",
`~/Projects/artemis-omni`) with `canonical_repo` `yazilimlar/artemis-omni`. DayOS therefore is a branch of
the Artemis Omni repository, not a repository of its own. The live checkout agreed with the registry
(same branch, same HEAD `1f9d2346e8ca`, clean). The link is *derived*, not declared, and only when exactly
one other product checks out the branch (`hostedSource`, `src/resources.ts`).

`tests/graph.test.ts` previously allowed only declared or observed edges; it now also allows a *derived*
edge, but only where its source names two registry rows. `tests/observe.test.ts` previously asserted a
one-entry allowlist; it now pins the exact two-entry set, so any further widening fails a test.

| Row | Kind shown | Provenance |
|---|---|---|
