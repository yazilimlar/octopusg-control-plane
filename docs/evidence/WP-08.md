## The three rules that are easy to get wrong

| Rule (docs/05 §3) | How it is kept, and how you can tell |
|---|---|
| Simulated events never feed KPIs | `kpiEligible` filters on `truth`, not on origin. Eight simulated fixtures yield **zero** countable events, and the banner prints that figure as a derived number. A test adds one `observed` event and the count becomes 1, so the exclusion is proven to be about truth rather than about fixtures. |
| Events are append-only | `appendStatusChange` returns a **new** array with a `event.status_changed` record carrying `correlation_id`; the original record still reads `new`. `currentStatus` is the fold. A test asserts the input log is byte-identical afterwards and that two changes both survive. |
| Duplicates de-duplicate on (connector, provider_event_id) | One fixture is a deliberate duplicate delivery of `mac-status|local-0001`. `duplicatesOf` finds exactly it, `dedupe` keeps the first delivery, and an event with no `provider_event_id` is never merged with anything — it has no provider identity. De-duplication is per connector: the same provider id under a different connector stays two events. |

## Privacy of the fixtures

No name, address, message body, IP address, serial number or user-bearing path appears in any
fixture, and the loader refuses a record that carries one — `carriesSecret` (WP-07) and
`carriesIdentifier` (WP-03) are reused rather than reimplemented, so the inbox inherits the rules
the connector and device records already live under. Summaries are capped at 200 characters so a
message body cannot be smuggled into one, and `payload_ref` must be a pointer.

## What the inbox does not do

Nothing is received: there is no webhook receiver, no polling, no provider client. Nothing is
counted. Nothing is edited — the screen is read-only, and status is shown as the fold over the
appended records rather than as a control. A local webhook receiver is v0.6 work and needs its
own ADR (OG-EVT-004).

## Documentation amended

`docs/05-EVENT-MODEL.md` §1 now names `source.provider_event_id`. The de-duplication rule in §3
already required it, but the envelope did not declare it, so the rule could not be implemented as
written. §3 also records what happens to an event that carries no provider id, and the shape of a
status-change record.

## A requirement proposed, not built

The owner supplied the **OctopusG logo** with this batch. No requirement covered a brand asset, so
per CLAUDE.md rule 3 it is recorded as **OG-UI-007 (PROPOSED, v0.3)** and **nothing was built**:
no image was committed, no favicon changed, no brand markup touched. Its source is `UNSOURCED`
(rule 4) and `npm run validate:spec` warns about that until the owner supplies one. Three things
need an owner decision before it can be implemented: which file is authoritative, the licence
position, and whether the wordmark's tagline belongs in the interface.

One repair was needed: `scripts/validate-spec.mjs` crashed when generating traceability for an
`UNSOURCED` requirement — the validator accepted the placeholder but the generator assumed every
source resolved to a file. It now renders `UNSOURCED` as plain text. No validation was weakened.
