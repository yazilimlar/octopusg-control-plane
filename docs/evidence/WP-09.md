## Safe open actions, and what makes them safe

| Action | What it is | What it can never be |
|---|---|---|
| Open website | `<a href>` to `projects[id].intended_url`, declared | a liveness claim — the note says so, and the app makes no request |
| Open repository | `<a href>` derived from `canonical_repo`, marked **derived** | invented — a row with no recorded remote gets no link |
| Open serving alias | `<a href>` to an alias recorded in `production_state`, marked **observed** | current — it is evidence of the moment it was captured |
| Copy folder path | text plus a Copy button | a link: `href` is `null`, and no `file://` URL appears anywhere |

`safeHttpsUrl` is the single gate every link passes. It refuses anything that is not `https:`, any
URL carrying credentials, any non-default port, **any query string or fragment** — so nothing about
the owner's workspace can ride along in a URL — and any bare IP address, so a link can never point
at a host on the owner's own network.

`npm run open` is the only thing that opens a folder, and it is deliberately narrow: it accepts a
**product id** and refuses a path outright; it looks the path up in the observer's own allowlist;
it applies the same device gate as observation, so an employer-owned or unenrolled device opens
nothing; it resolves the path canonically through `resolveTarget`, so a symlink cannot redirect it,
and the path must still be a Git repository; it calls a fixed per-platform opener through
`execFileSync` with one argument and no shell; and it writes nothing, reads nothing from the
repository and does not print the path.

## The action request, as outcomes rather than prose

`config/action-requests.json` holds seven example requests, each marked `simulated`. The Approval
queue runs each through `decide()` — the same pure function the tests assert against — and prints
the reason exactly as returned. Three of the refusals are the ones worth reading:

- **`rotate-dns-record` (T4, level 4)** — *level 4 is never available for T4*. Controlled
  automation is unreachable for a critical action even with an approval and a template recorded.
- **`promote-deployment` (T3)** — the tier, level and approval all pass, and it is still refused:
  *needs all seven fields in docs/06 §3*, naming the four that are missing.
- **`observe-from-company-laptop` (T0)** — *trust zone employer permits no OctopusG action*, at
  the lowest tier there is.

Two facts the examples made visible, which are worth the owner's attention: a zone is checked
**before** tier, level and the record, and **no declared trust zone permits T3 or T4 at all** — the
personal zone caps at T2 and every other zone permits none. A production action in v0.2 therefore
has nowhere it could run, which is the intended posture and is now asserted by a test.

A present dossier field is owner-supplied text, not proof: OctopusG checks that the record exists,
never that it is true. An AI recommendation is never sufficient on its own.

## Nothing can execute

`src/actions.ts` imports no `child_process`, exports no `execute`, and a test asserts both. The
only process this repository spawns is the fixed folder opener in `scripts/open.mjs` and the five
read-only Git commands in the WP-03 observer. The Approval queue offers no Execute, Run now or
Approve-and-run control, asserted in the browser.

## Open questions

- **No declared trust zone permits T3 or T4.** The personal zone caps at T2 and every other zone
  permits none, so a production or critical action has nowhere it could run. That is the intended
  posture for v0.2, but the owner should confirm it is the intended posture for v0.3 as well.
- `npm run open` uses the observer's allowlist, which currently lists one repository. Opening a
  folder that is not a Git repository is refused; whether plain folders should be openable is
  undecided.
- The example action requests are illustrative. The real set of action types belongs to the blocks
  that introduce them (v0.5 and v0.10).
